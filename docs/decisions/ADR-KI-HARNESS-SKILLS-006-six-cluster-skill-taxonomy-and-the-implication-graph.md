# ADR-KI-HARNESS-SKILLS-006: Six-cluster skill taxonomy and the implication graph

## Context

The skill set grew to twenty without a stated organising model. The README described relationships in prose and ASCII art, and the only machine-readable substrate was `ki-repo`'s coverage array plus `ki-bootstrap`'s two-element baseline. Two things were missing: a named taxonomy that says what role each skill plays, and a single declared source for "linking skill X pulls in skill Y" that both the bootstrap chain and a user-facing dependency tree could derive from without drifting apart.

## Decision

The skills are organised into six clusters, and their relationships are declared in a machine-readable implication graph.

- **Kind axis (orthogonal to the clusters).** Every skill has a **kind** — **governance** or **process** — cutting across the six clusters. A **governance skill** holds a house standard and ships the universal modes (AUDIT/CONFORM/EDUCATE/REFRESH + HELP, [ADR-KI-HARNESS-SKILLS-001](ADR-KI-HARNESS-SKILLS-001-audit-conform-educate-refresh-canonical-modes-help.md)) and the four-file shape (`<domain>standards.md`, `rubric.md`, `sources.md`, a mechanical checker), which the `ki-skills` rubric enforces. A **process skill** drives an action or lifecycle rather than holding a standard: it is lightweight, may bundle a helper `scripts/` and a `references/` procedure (the "extra gubbins" a plain `.claude/commands/*.md` cannot carry), and is **exempt** from the governance four-file shape and universal modes — its mode count varies and it exposes HELP only optionally. Both kinds are dual-invocable (`/<name>` explicit and model-triggered by `description`); a process skill is a slash command with a script and references attached. The process skills are **`ki-recap`** (a light one-mode skill — summarise / surface-outstanding / harvest-learnings over a live session, with an optional current-session handoff to `ki-next`), **`ki-next`** (the confirmation-gated next-work selector), **`ki-plan`** (the non-KB work-item planning lifecycle through Ready), **`ki-implement`** (bounded Ready → Acceptance delivery), **`ki-accept`** (human-approved closure and pruning by explicit roadmap-item path or glob), **`ki-batch`** (explicitly authorised coordination of independent delivery cycles), and **`ki-delegate`** (banks planning reasoning in cold-agent-ready briefs, then classifies, assigns, sequences, and gates execution across agents and per-spawn models). Human-led repository review is the `REVIEW` mode of the governance skill `ki-repo`, so it follows the repository's declared capability rather than being installed globally. At a safe high-context recap-to-new-work boundary, `ki-recap` preserves its carry-forward digest and invokes the current runtime's native compaction control when available; true window reduction remains the native / PreCompact-hook path (`ki-tokenomics`), not a portable token counter invented by the skill. Kind is orthogonal to **install scope** (global vs project-local): `ki bootstrap` installs the process skills globally, for the same reason as the keystone `ki-bootstrap` — utility across any repo on the machine, not repo governance — and like `ki-bootstrap` they are therefore **never vendored or declared** in a repo's `.ki-config.toml` (no process-skill table, including `ki-delegate`, `ki-next`, `ki-plan`, `ki-implement`, `ki-accept`, `ki-batch`, or `ki-recap`, ever); a governance skill's `[ki-<skill>]` table means "this repo is governed by this standard," which does not apply to a process skill with no standard to be governed by.
- **Clusters.** (1) **Keystone** — `ki-bootstrap`, `ki-repo`. (2) **Foundations** (structure-independent governance) — `ki-authoring` and `ki-engineering`. (3) **Repo-structure**, mutually exclusive, exactly one per repo — `ki-harness`, `ki-kb`, `ki-website`, `ki-mcp`, `ki-plugins`, `ki-specifications`, `ki-tools`, `ki-homebrew-tap`, `ki-dotfiles-chezmoi`. `ki-specifications` begins as a deliberately minimal structural floor: a keyless marker and the established top-level authority/supporting areas, with deeper rules factored in only after they stabilise. (4) **General governance** — `ki-subagents`, `ki-skills`, `ki-decision-records`, `ki-feature-definitions`, `ki-guides`, `ki-roadmap` (non-KB repositories only). (5) **Dependent families** — `ki-kb-streams`, `ki-kb-activities`, `ki-kb-live-artifacts` (the KB family required by `ki-kb`), `ki-website-cloudflare` (the website family required by `ki-website`), `ki-binding-chezmoi` (the binding family required by `ki-binding`). (6) **Environment** — portable `ki-binding` and `ki-tokenomics`; runtime adapters `ki-binding-claude`, `ki-binding-codex`, `ki-tokenomics-claude`, and `ki-tokenomics-codex`; vendor-bound `ki-housekeeping-claude`; and renderer-specific binding skills.
- **Physical layout.** The six clusters are also physically encoded: every skill lives at `skills/<cluster>/<name>` (cluster names kebab-case per the list above — `keystone`, `foundations`, `repo-structure`, `general-governance`, `implied-families`, `environment`), not the earlier flat `skills/<name>`. Process-kind skills live under a seventh, **physical-only** `skills/process/` directory — this is not a seventh conceptual cluster; kind remains the orthogonal axis, and `process/` simply gives it a physical home the way the six clusters give the cluster axis one. The cluster (and `process/`) subfolder is a filesystem grouping only: the canonical skill **name** referenced everywhere else (`.ki-config.toml`, `ki-depends-on:` frontmatter, package.json script bodies) stays the bare `ki-<name>`, never the path — `skills/keystone/ki-bootstrap/scripts/resolve.ts` resolves a bare name to its on-disk cluster path via a memoized index, so no consumer outside that resolver needs to know which cluster it lives in.
- **Dependency graph.** Each SKILL.md declares a `ki-depends-on:` frontmatter list. A dependency identifies a necessary governance prerequisite: selecting the dependent includes the prerequisite first, while independent skills receive a stable host-defined order. The list's textual order is never semantic; an additional edge expresses any further required partial order. A repo declaring a skill MUST explicitly declare each dependency in `.ki-config.toml`; activation and repository resolution reject a missing declaration before mutation or execution. Separately coverage-detected governance adds no dependency edge.
- **Universal vs coverage-detected.** `ki-authoring` is a universal requirement of `ki-repo`, declared by its `ki-depends-on:` edge and explicitly present in each repo's configuration. `ki-engineering` governs the TS/Bun toolchain, which only exists where a `package.json` does — it remains **coverage-detected**: `ki-repo`'s coverage cascade expects `["knowledgeislands/ki-agentic-harness:ki-engineering"]` to be declared by any repo with a `package.json`, and only then does it get vendored/linked. A non-code repo (dotfiles, a KB, the homebrew tap) carries neither that table nor an inactive edge.
- **Mutual exclusion.** A repo carries exactly one repo-structure skill; `ki-repo`'s coverage cascade enforces it mechanically.
- **Canonical names.** Each skill's directory name is its canonical name. A portable root keeps the unqualified concern name; a runtime-bound capability uses the runtime suffix and declares its supported runtimes in frontmatter. `ki-feature-definitions` is the general-governance skill for feature specs; `ki-guides` governs repository-local practical documentation.

## Consequences

- A new skill is placed by choosing its cluster; its edges are declared in one greppable place.
- The user-guide tree cannot drift from the dependency graph; a broken edge fails CI. Bootstrap validates dependencies against explicit repository declarations rather than treating the graph as a coverage-expansion mechanism.
- Cluster 6 gives the machine/environment skills a home the earlier repo-only taxonomy lacked.
- The generated plugin-marketplace repo (`knowledgeislands/ki-plugins`, `ADR-KI-HARNESS-002`) is a further repo shape; `ki-plugins` governs its on-disk projection so it is no longer a repo carrying zero repo-structure skills. Its **generation and cross-surface enablement** stay with the environment skill `ki-binding` (they govern the machine, not the repo) — the split keeps each cluster's defining property intact.
- Runtime adapters stay in the Environment cluster. Their `ki-supported-runtimes` and `ki-runtime-binding` metadata make compatibility machine-readable without creating another taxonomy cluster.
