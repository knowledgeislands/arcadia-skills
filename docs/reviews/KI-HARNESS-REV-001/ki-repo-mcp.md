# `ki-repo-mcp` effectiveness review

- **Review state:** complete, ungraded
- **Candidate disposition:** revise
- **Change state:** review only; no Phase 4 remediation is authorised

## Dependency and ownership

`ki-repo-mcp` provides a distinct and economical server-code standard, while correctly routing canonical runtime inventory and client targeting to `ki-binding`. Its safe conform boundary is valuable. Substantial report-only binding and connector detail remains embedded here, however, creating duplicated standing context and future semantic-forwarding risk.

All six current MCP repositories declare the skill and pass focused audit. The source registry still names two retired repository locators and is overdue for its monthly refresh. Official MCP sources also make clear that tool annotations are untrusted hints, not security enforcement.

## Mechanical trace and limits

Nine tests, publication, type-checking, and six focused audits pass. The checker coherently covers marker, layout, document, token, utility, package, script, and CI presence, with symlink-safe bounded proposals.

A clean result does not establish dependency injection, no singleton, config-first calls, access-gate registration, annotation use, redaction, containment, bounded schemas, dry-run defaults, or OAuth behavior. These remain judgment prompts. `TOOL-1` uses whole-source word presence, so an unrelated schema can mask a per-tool result mismatch, and registration ordering recognizes only direct forms. Three evals test vocabulary recall, not security or protocol outcomes.

## Candidate improvements

1. Refresh all six primary repository identities, dates, and protocol watch-items without asserting unsupported locator continuity.
2. Add bounded per-tool fixtures for gated registration, annotation use, schema/result pairing, bypass attempts, and representative failure envelopes.
3. Keep dynamic security judgment explicit, and do not present structural success as protocol, binding, reachability, or safety evidence.
4. Decide whether report-only runtime detail should become concise routing to binding-owned references, without changing ownership during this review.

## Carry-forward criteria

Server structure does not prove a server is bound, enabled, reachable, protocol-current, or safe. Security-significant claims need per-operation evidence and cannot rely on untrusted metadata hints.
